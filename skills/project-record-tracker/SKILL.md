# Project Record Tracker

本技能用于把一次任务、一个阶段、一个完整项目或一组工作材料整理成可追溯的项目记录。它关注“事实留痕”和“后续可用”，不是只写一段漂亮总结。

项目记录主要服务两个场景：

1. 用户后续回看项目时，可以快速知道项目什么时候开始、什么时候完成、期间做了什么、产出了什么、哪些结论有证据。
2. 用户编写简历或准备面试时，可以从事实记录中裁剪出不夸大的项目经历、能力亮点和追问答案。

## 核心原则

1. 证据优先：项目时间、工作内容、产物和结论必须尽量回到会话上下文、文件内容、文件时间、Git 记录、报告、数据、截图或命令输出。
2. 不编造时间：没有证据时，不得伪造项目开始时间、完成时间、耗时、参与人数、使用次数、收益或影响范围。
3. 区分确定与推定：时间和成果分为 `确认时间`、`推测时间`、`待确认`，结论分为事实、推断和待补充。
4. 保护隐私和凭据：不要读取 `.env`、密钥、token、私钥、系统凭据、聊天账户数据或无关个人文件，除非用户明确指定且说明用途。
5. 原始材料优先：不要覆盖、移动、清空旧报告、原始数据和历史记录。项目记录应输出为新文件，或在用户要求时更新指定文件。
6. 面向复用：先重建事实和证据，再从事实中提炼简历素材和面试材料。

## 适用场景

- 用户完成一个项目后，希望生成项目记录、项目复盘或项目台账。
- 用户有一批报告、代码、数据、提示词、skills、agents、文档，想整理成可追溯记录。
- 用户想把某段工作经历提炼为简历项目、个人能力介绍或面试材料。
- 用户需要从 AI 会话、工作目录和生成文件中恢复“这段时间到底做了什么”。
- 用户需要整理项目开始时间、完成时间、关键阶段节点、主要工作内容和关键产物。

## 默认输出

默认每次生成一个 Markdown 项目记录文件，除非用户明确要求其他格式。

输出位置：

- 如果用户给出路径，写入用户指定路径。
- 否则在当前工作区创建或更新：

```text
project-records/<YYYY-MM-DD>_<项目简称>_项目记录.md
```

如果同名记录已经存在，先读取原文，谨慎更新；保留用户已写事实，除非更强证据显示需要修正。

正文默认使用中文。

## 证据来源

按可用性和相关性逐层收集，不要为了完整而读取大量无关文件。

| 来源 | 用途 | 注意事项 |
|---|---|---|
| 用户请求和当前会话上下文 | 识别目标、关键决策、任务变化、用户确认事项 | 会话内容可用，但未确认内容不要写成事实 |
| README / AGENTS / CLAUDE / DESIGN / 项目规则 | 获取项目定位、工作方式、边界和使用说明 | 优先读取项目根目录附近的规则 |
| 生成的报告、总结和文档 | 提取工作内容、结论、产物、待确认问题 | 保留路径，避免改写成无法追溯的泛化表述 |
| 工作目录文件 | 识别实际产物、目录结构、脚本、数据、配置 | 大目录先列结构，再按文件名和时间筛选 |
| 文件元数据 | 推定开始时间、最近修改时间、产物生成时间 | 只能作为推定证据，不等于真实工作开始时间 |
| Git 记录 | 获取提交时间、变更主题、版本演进 | 没有 Git 或记录不完整时说明缺口 |
| diff、命令输出和日志 | 记录验证方式、运行结果、失败原因 | 工具失败不是业务结论 |
| 用户补充说明 | 补齐缺失时间、角色、背景、影响范围 | 标注为用户确认 |

不要把未读取的文件列成证据。

## 工作流程

### 1. 识别项目范围

推断项目名称和边界：

- 优先使用用户明确给出的项目名。
- 否则从仓库名、主报告、主模块、主目录或任务主题推定简短名称。
- 区分整个仓库和本次需要记录的具体项目/任务。
- 如果只是大项目中的一个阶段，命名为阶段记录。
- 范围不清时，把边界写入“待确认”，不要自行扩大到无关目录。

### 2. 重建项目时间线

构建实用时间线，不追求完美取证。

可用证据包括：

- 会话时间或用户明确说明。
- 文件创建/修改时间。
- 报告日期。
- Git 提交时间或 diff 历史。
- 任务清单、日志、笔记中的顺序信息。

时间精度要诚实：

- `确认时间`：有明确时间戳证据支持。
- `推测时间`：从文件修改时间、目录变化或上下文推断。
- `待确认`：当前证据不足。

始终包含：

- 项目开始时间。
- 项目完成时间或当前状态。
- 关键阶段节点。
- 未完成或待验证事项。

不要把文件修改时间直接写成真实工作时间。推荐写法：

```text
根据当前可见文件时间推定：...
```

### 3. 提取主要工作内容

将工作归纳为 3 到 7 个主要模块。

每个模块写清：

- 做了什么。
- 为什么要做。
- 使用了哪些方法、工具、文件或数据。
- 产出了什么。
- 证据位置。
- 当前可信度：`高 / 中 / 低`。

优先使用具体动词：`定位`、`还原`、`验证`、`实现`、`修复`、`整理`、`对比`、`生成`、`审校`。

### 4. 分离事实和表达

保持三层分离：

1. `事实记录`：受证据约束的项目历史。
2. `简历素材`：角色、难点、方法、成果和能力提炼。
3. `面试追问`：用户需要准备解释的问题。

这种分离很重要，因为项目记录、简历条目和面试话术的表达边界不同。

### 5. 生成项目记录

默认使用以下结构：


## 字段写作规则

### 记录元信息

每个关键字段都写依据和可信度。不要只写值。

可信度建议：

- 高：来自用户明确说明、文件正文明确记录、Git 提交记录或明确时间戳。
- 中：来自文件名、目录结构、文件修改时间和上下文综合判断。
- 低：证据较弱，仅能作为线索。
- 待确认：当前证据不足。

### 信息来源

列出实际用于生成记录的材料：

- 会话上下文。
- 文件路径。
- 报告路径。
- 数据路径。
- Git 记录摘要。
- 用户补充说明。

### 时间线

按时间升序组织。时间不确定时可以写“约”“推定”“晚于/早于”。

### 关键产出

产物包括但不限于：

- 报告。
- 脚本。
- skills。
- agents。
- prompts。
- 数据文件。
- 截图。
- 配置文件。
- README 或说明文档。

每个产物尽量写路径、用途和状态。

### 简历项目经历素材

从项目记录中裁剪，不要凭空拔高。

至少包含：

- 完整版项目描述。
- 精简版简历项目。
- 可提炼能力。
- 面试一句话版本。
- 面试追问准备。

### 后续可补充指标

如果缺少量化数据，列建议补充项，例如：

- 项目周期。
- 文件/报告/脚本数量。
- 复用次数。
- 节省时间。
- 处理样本数量。
- 审查发现问题数量。

不要把建议指标写成已发生事实。

## 输出边界

1. 不写无法回查的项目成果。
2. 不把 AI 生成内容自动当成事实；AI 生成内容要结合文件、用户确认或实际产物判断。
3. 不把文件修改时间等同于真实工作时间；只能作为推定依据。
4. 不读取无关个人目录，不扫描凭据文件。
5. 不为了简历好看而夸大项目规模、影响、角色或结果。
6. 不覆盖原始材料。

## 交付自检

输出前检查：

1. 是否写明项目开始时间、完成时间或当前状态，无法确认时是否标为待确认。
2. 是否列出信息来源和证据路径。
3. 是否区分确认时间、推测时间、待确认内容。
4. 是否包含主要工作内容、关键产物、当前状态和后续事项。
5. 是否提供简历项目经历素材和面试追问准备。
6. 是否避免夸大、编造和无证据结论。

## 最终回复

保持简短：

- 说明保存的文件路径。
- 概括包含的主要章节。
- 提醒重要缺失证据或假设。
- 如有用，建议下一步可继续生成：`简历精简版`、`面试问答版` 或 `项目复盘版`。
