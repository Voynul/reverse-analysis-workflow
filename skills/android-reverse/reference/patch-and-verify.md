# APK 修改与验收

## 使用边界

只有用户明确要求修改、重建或输出可安装 APK 时使用。默认分析任务不得自动进入本流程。始终保留原始 APK，产物写入独立目录。

## 原始产物身份

开始前记录：

- 原始 APK 的绝对路径、文件大小和 SHA-256。
- 包名、`versionName`、`versionCode`、min/target SDK。
- ABI、DEX 数量和签名摘要。
- 原始包能否安装、启动并到达目标路径。

原始文件不可覆盖；所有解包、修改、签名和安装产物使用明确的新名称。

## 对照基线

在业务修改前验证工具链本身：

1. 对原始包执行必要的解包或读取操作。
2. 进行零逻辑修改重建，或使用最接近实际修改路径的控制流程。
3. 完成对齐、签名、安装和冷启动。
4. 记录与原始包的预期差异和异常差异。

对照基线失败时停止业务修改，先处理构建、签名、安装、架构或环境问题。

## 工具与路径选择

Apktool 是 smali、Manifest 和资源修改的首选解码与重建工具。根据修改范围选择最小路径：

| 修改类型 | 首选路径 | 目的 |
|---|---|---|
| 仅资源 | 保留 DEX 的资源解码路径 | 避免无关 smali 重组 |
| 仅 smali | 保留资源表的源码解码路径 | 降低资源重编译差异 |
| Manifest、资源与 smali 联合修改 | 完整解码后重建 | 允许构建工具同时处理资源和 DEX |
| 仅替换 `.so` 或 assets | 优先使用能保留其他归档条目的最小替换流程 | 避免无关资源和 DEX 变化 |
| DEX/JAR/smali 专项转换 | 当前环境中与任务匹配的 DEX 工具 | 只处理 Apktool 不适合表达的 DEX 转换或诊断 |

保留源码或资源的选项不能机械套用。修改目标依赖资源 ID、Manifest 合并、DEX 结构或构建工具生成文件时，应使用能够完整表达修改的路径。DEX 专项工具不进入普通 Apktool 重建链，使用前先保存输入哈希并验证输出 DEX 能被解析。加固、Flutter、Unity 或动态加载目标先确认真实逻辑归属；split APK、APKM 和 XAPK 先确认完整安装集合，不能只处理 `base.apk` 后宣称完成。

进入修改分支后才检查解码、构建、签名和安装能力。当前任务第一次使用某项工具时记录实际版本和关键配置，工具和环境未变化时不重复检查。

## 重打包时的归档保留

选择归档替换或排查重建差异时，关注与实际加载有关的内容：

- 清除旧签名时只处理已确认的签名产物，不删除整个 `META-INF/`。其中的 `META-INF/services/` 等条目可能参与运行时加载。
- 对未修改条目，同时比较内容和压缩方式；只比较解压后的哈希会漏掉压缩属性变化。资源表及未压缩 native 库的对齐按目标平台要求验证。
- 资源重编译、索引重排或资源路径重命名可能产生大量差异。结合内容、资源引用和对照重建区分预期变化与异常变化，不根据差异数量直接判定失败。
- 仅修改 DEX 时，可以比较保留原归档并替换目标 DEX 与完整重建的成本；选择能够满足修改目标且经过验证的路径，不固定优先级。

## 修改声明

每个修改项记录：

| 字段 | 内容 |
|---|---|
| 目标 | 文件、类、方法、资源、native 函数或偏移 |
| 原始行为 | 修改前证据和触发条件 |
| 预期行为 | 修改后需要观察到的结果 |
| 修改方式 | smali、DEX、资源、配置或 native 修改 |
| 影响范围 | 直接影响和可能回归范围 |
| 验证方法 | 静态差异、安装、运行路径、Hook 或网络证据 |

只修改完成目标所需的最小范围。不要把重命名、格式化、去混淆或无关修复混入同一产物。

## 构建与安装

选择当前环境中经过验证、能够满足任务签名要求的工具。通用顺序为：

```text
重建
→ 必要的对齐
→ 签名
→ 签名和对齐验证
→ 安装、冷启动和目标行为验证
```

如果使用一体化签名工具，确认其同时完成必要的对齐和最终验证；如果分开使用 `zipalign` 与 `apksigner`，必须先对齐再签名。签名后不得再修改 APK。包含未压缩 `.so` 时使用支持相应页对齐要求的工具和参数。所有步骤使用独立输出文件或目录，不覆盖原始 APK。

依次记录以下独立状态：

1. 修改内容写入成功。
2. DEX、资源或 native 文件结构有效。
3. APK 重建成功。
4. 对齐和签名成功。
5. 安装成功；如覆盖安装失败，区分签名、版本、权限和设备策略原因。
6. 冷启动成功，无新增崩溃或明显初始化异常。

每一步失败都保留真实错误，不用后续步骤掩盖前序失败。

## 签名与安装约束

- Apktool 不负责最终签名；根据当前环境、签名方案和验证要求选择签名工具。
- 不在命令、脚本、状态文件或日志中写入密钥密码；优先使用标准输入或受控凭据来源。
- 研究用签名密钥与原应用签名通常不同，修改包通常不能直接覆盖安装原签名应用。需要保留应用数据或验证升级路径时，应先确认是否具备原签名或受控测试签名。
- 卸载原应用会删除其私有数据，执行前必须获得用户明确授权并记录影响。
- 签名校验、防篡改、完整性校验、服务端校验或 Play Integrity 可能使重签名包启动失败或行为变化；这类失败应单独分析，不能归因为 Apktool 重建失败。
- 原应用读取自身签名证书时，检查该值是否参与请求签名、解密或初始化参数派生；按需参照 `algorithm-validation.md`，不要仅凭网络失败认定是完整性检查。
- split APK 使用与目标一致的完整安装集合验收；单独安装修改后的 `base.apk` 不代表 split 应用可用。

## 运行验收

1. 重现原始目标路径和触发条件。
2. 观察目标行为是否按修改声明变化。
3. 使用 UI、Hook、日志、抓包或文件状态提供运行证据。
4. 检查相关但未修改的关键路径，识别直接回归。
5. 将主动 Hook 干预与修改 APK 的自然运行结果分开记录。

交付要求涉及持续生效时，按需要检查重启、缓存回写、远程配置刷新或干净安装后的表现；不要求每个任务都执行全部场景。当前设备的数据编辑、文件锁定或持续 Hook 依赖应如实说明，不能据此声称效果已包含在 APK 中。需要清数据或卸载时，先遵守既有授权和数据保护边界。

## 修改审计

- 对比原始包、对照重建包和最终修改包。
- 分别判断修改是否到达最终产物，以及结果能否被正确解析和执行。等长修改也可能改变行为，不能只按文件大小或方法长度筛选；直接核对修改声明中的目标方法、指令或偏移。
- 检查修改声明之外的 DEX、资源、Manifest、so、归档属性和签名差异。常量池索引等重排可能改变字节而不改变语义，必要时结合反汇编核对。
- 原位修改 DEX 字节时，用可靠实现重算并验证头部完整性字段。汇编和校验通过仍不等于运行验证通过；涉及指令修改时，按影响范围检查指令边界、寄存器类型、结果生产与 `move-result*` 的相邻关系及控制流。局部扫描器不能替代完整验证，回归判断也不能只比较问题总数。
- 工具报告已应用但效果未变时，核对最终文件、安装包身份和实际加载的代码副本，排除旧构建或目标不一致；不要仅重复执行同一补丁。
- 搜索原始目标逻辑或字符串是否仍有未预期残留。
- 不能证明的效果标为未验证，不因 APK 能安装就判定完成。

## 交付

交付内容至少包括：

- 最终 APK 的路径、大小、SHA-256 和签名信息。
- 修改声明和实际差异摘要。
- 构建、安装、启动和目标行为的独立结果。
- 已知限制、未完成项和复现步骤。

用户未要求正式报告时，以上内容可以直接在对话中交付；只有任务需要持久化或恢复时才写入 `analysis-state.md`。

方法参考：`apk-reverse-codeberg-mirror` 中 `apk-reverse` 的补丁审计、归档保留和运行数据诊断经验；已独立整理为按需建议，不依赖上游脚本或强制流程。
