# 检测、反分析与观测故障诊断

用于 attach 后退出、启动拒绝、零事件、挂起、root/模拟器/调试器检测等问题。目标是找到足以解释现象的证据，不把隐藏、禁用检查或切换静态设为统一答案。

## 可比较的条件

按现有证据选择对照：同一构建无注入、只加载观察脚本、带目标 Hook 或主动修改。先确认原包在当前环境的表现；原包也失败时，不能把失败全部归于补丁。

| 现象 | 候选原因 | 可区分的证据 |
|---|---|---|
| attach 卡住或报进程消失 | 进程状态、权限、ABI/翻译层、工具问题或检测 | 实际 PID/状态、进程 ABI、连接错误和合适的对照进程 |
| 脚本加载后立即退出 | API/脚本错误、时序、资源影响或 RASP | 脚本自身健康事件、错误消息、无脚本/最小脚本对照 |
| Hook 零次命中 | 目标未走、加载器/重载错误、安装过晚或消息丢失 | 已知会执行的控制点、实际绑定、消息链路与覆盖时间 |
| 进程活着但 UI 不动 | 暂停、死锁、错误 keepalive、自旋或 ANR | 线程状态、交互结果、干预点和等待条件 |
| 无 Java 栈或 tombstone | 主动退出、日志缺失或其他终止路径 | 信号、系统记录、进程生命周期及调用来源 |

控制点应尽量与问题接近，但不要为了验证工具去操作无关应用或账户。没有有效对照时保留不确定项。

## 定位检测来源

按问题可以观察文件/包查询、加载、线程、进程控制、时间及 JNI/Java 检查。重点记录调用者模块、相对位置、时机与参数，缩小到真正相关的检查；不要求全量 Hook 所有 API。

早于 Hook 的检查可能位于构造器、加载器或运行时初始化。核对实际符号、调用顺序和载荷作用；壳构造器也可能负责业务解密，清空整个初始化表会破坏目标。

内联 syscall、间接调用、运行生成代码或其他模块可能绕过某个 API Hook。某库的静态扫描未发现指令，只能限定该输入与扫描覆盖，不能证明整个进程不使用该机制。

## 观察与干预

观察模块与改变返回值、阻断退出、延迟线程等干预最好在可区分的实验条件下使用。只观察的 Hook 本身仍可能改变代码、映射、时序和资源，不称为未经触动的原始进程。

信号、故障地址与所属模块一起判断；运行时可使用内部故障处理机制，不能把所有 SIGSEGV 都当成目标自毁或无条件吞掉信号。

`Seccomp`、`TracerPid`、可疑路径、root 模块或映射是线索，不是单独的检测成功证明。确认谁读取、何时读取，以及结果如何进入决策。

## 选择下一步

- 需求是理解逻辑时，可以用静态、原函数调用或另一种观测补证。
- 需要改变目标行为时，先确认修改范围和调用语义，再选择局部干预；不把普遍伪造系统信息作为默认方案。
- 替代设备、调试协议或硬件观测是候选，不承诺规避所有检测。比较实际依赖、成本和所需证据。
- 检测只影响当前分析环境，与会跟随交付产物的完整性或签名问题分开判断。
- 等待、重试与升级根据新信息是否可能改变结论决定；不要通过固定次数判定某种技术永远不可用。
