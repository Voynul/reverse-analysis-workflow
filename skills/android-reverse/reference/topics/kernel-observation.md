# root 暴露、内核观测与环境边界

当问题确实需要区分用户态、系统和内核能力时读取。保留高级方法不代表当前环境具备实现，也不要求在用户态失败后自动升级。

## 分层判断

root 实现、用户态模块、Zygisk/框架注入、ptrace、驱动和内核插桩是不同交付与执行层。管理器存在、模块文件生成、脚本返回成功都不能证明内核逻辑已生效。

用户态 Hook 观察不到某次调用，可能因为覆盖或时机，也可能因为直接 syscall、另一进程或权限边界。先取得与问题有关的证据，再选择是否进入更低层。

## 暴露与隐藏

路径、挂载、包、进程、映射、线程、调试状态和时间都是候选表面。隐藏一个字符串不等于隐藏实现，也可能破坏应用自身加载或解析。

环境隐藏模块可以有兼容性、冲突和版本依赖。不要无依据叠加模块、修改全局策略或宣称绝对不可检测；分析环境依赖与交付物要求分开。

## 内核能力的前提

评估硬件、内核配置、接口、权限、构建链、对应头/源码、模块 ABI 及目标版本。eBPF、perf、KPM/LKM 等支持按真实环境确认，不能用单一内核版本阈值断言全部能力。

普通用户态启动脚本或 root 模块不自动具有修改内核 syscall 返回值的能力。操作发生在哪一层、能读取或改变哪种上下文，要由真实接口与结果说明。

事件、断点或寄存器改写属于主动干预。构建与加载可能影响系统稳定性，只有明确属于任务范围时才实施；模板不作为已运行工具交付。

## 验证边界

将主机生成、静态检查、编译、模块加载、控制点命中、目标观测与业务影响分别记录。即使不修改目标代码，也不能承诺无时序、状态或可见性影响。

本技能未迁入内核生成器或驱动，相关内容为可选路线与验证依据。实际可用性见 [专项工具](../tools/specialists.md)，问题归因见 [反分析](anti-analysis.md)。
