# LSPosed / Xposed 与模块式交付

用户允许运行时模块、持久化 Hook 或研究其实现时使用。模块与重建 APK、主机代理、设备数据修改是不同交付物，不因重签受阻自动替换用户目标。

## 可实现的边界

定位目标方法、包/进程作用域和 ClassLoader，再判断方法 Hook 是否能表达所需效果。Java 层替换不能自动改变 native、远程权限或未经过该方法的路径。

参数、返回、异常、调用前后和调用原实现的语义要区分；构造器、多重重载、协程与异步回调可能改变安装和触发位置。不要把某个 helper 变为常量作为通用方案。

## 模块与环境

确认实际框架/API、目标应用版本、进程和激活条件。构建工具链可按环境选择，不要求 Gradle 或无 Gradle 的固定路线；依赖、作用域、入口及 ABI 按所用实现核对。

需要不依赖完整项目构建器的路线时，可按当前 API 组织编译、DEX 生成、Manifest/资源处理、归档与签名，并核对框架要求的入口资产和元信息。某个生成的 APK 能安装，只能证明安装阶段，不能证明框架会识别或加载它。

设备拥有管理器不证明框架在目标进程激活。日志输出、框架日志和目标方法执行分别核对，日志通道损坏时不能直接判模块未运行。

框架自身可能引入映射、时序和检测线索。保留不加载模块与目标模块的可比较条件，不默认安装隐藏模块或改变系统。

## 验收与交付

验证模块加载、Hook 安装、目标方法实际命中和业务变化。重启、进程重建、应用更新、作用域变化及框架依赖按交付要求测试。

明确结果需要什么设备条件、模块与框架、支持哪个版本及哪些分支未覆盖。源码或脚手架生成、APK 构建、模块启用、功能生效不是同一个完成状态。

本技能没有迁入上游模块/内核生成器。实际实现按 [专项工具](../tools/specialists.md) 选择，行为判断见 [动态 Hook](../dynamic-hook.md) 与 [反分析](anti-analysis.md)。
