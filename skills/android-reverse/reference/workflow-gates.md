# Android Reverse 任务关卡

## 任务模式

| 模式 | 触发条件 | 默认行为 |
|---|---|---|
| `analysis` | 默认；用户要求理解、定位、解释或还原逻辑 | 只读分析，不修改 APK |
| `runtime-validation` | 需要 Hook、设备操作、抓包或真实样本验证 | 保留原始运行结果，主动干预单独标记 |
| `patch-and-verify` | 用户明确要求修改、重建或输出可安装 APK | 建立基线、最小修改并完成构建到运行验收 |

一个任务可以从 `analysis` 增加 `runtime-validation`，但进入 `patch-and-verify` 必须有用户明确请求。只有已经使用状态文件时才同步模式变化。

## Gate 0：授权、目标与交付物

开始前确认：

- 目标属于用户拥有、获准测试或明确的研究、教学、竞赛范围。
- 当前目标或目标集合身份明确；涉及版本对比、split 集合或关联载荷时分别隔离证据。
- 交付物是对话结论、脚本、证据、修改 APK、验证记录或正式报告。
- 普通分析默认直接回答；交付物差异不会改变执行路径时不额外追问。

未通过时停止会改变外部状态的步骤，只能继续不依赖缺失信息的只读检查。

## Gate 1：环境预检

按任务模式做最小检查：

- `analysis`：第一次需要静态分析时确认目标文件和静态分析能力。
- `runtime-validation`：实际使用设备、Hook 或抓包分支时，再分别检查对应能力。
- `patch-and-verify`：实际进入解码、构建、签名或安装步骤前，再检查工作目录、可用磁盘、相关工具、签名材料和设备环境。
- native 分支：第一次进入 native 分析时确认无头分析能力、目标架构和反编译状态。

工具检查结果在当前任务内复用。工具或设备未变化时不重复健康检查；长任务需要跨会话恢复时才将检查时间、版本和连接方式写入状态文件。

缺少工具时记录受影响分支，不把工具不可用解释为目标不存在。

## Gate 2：关键逻辑归属

在深入追踪或修改前，判断关键逻辑主要属于：

- DEX 中的 Java/Kotlin/smali。
- Manifest、资源或配置。
- native so/JNI。
- Flutter/Dart AOT。
- Unity/IL2CPP。
- WebView/JavaScript。
- 服务端或远程配置。
- 尚未确认。

若多个层共同参与，说明控制点和数据边界。长任务或需要恢复时将归属判断及置信度写入状态；详细规则见 `package-recon.md`。

## Gate 3：修改基线

仅 `patch-and-verify` 使用：

1. 记录原始 APK 路径、大小、SHA-256、包名和版本。
2. 保留原始 APK，只在独立工作目录操作。
3. 根据修改类型选择能够完整表达目标变更且引入无关差异最少的处理路径。
4. 在业务修改前使用与最终产物相同的路径建立零逻辑修改或等价对照基线。构建默认不得无意开启调试属性；最终路径不经过完整重建时，至少用相同归档、对齐和签名流程建立对照。
5. 对 split APK、APKM 或 XAPK，先确认完整安装集合和交付形式，不把仅修改 `base.apk` 默认视为完整产物。
6. 基线失败时先定位构建、签名、安装或环境问题，不进入业务修改。

## 长任务纪律

分别维护分析、修改、构建、安装、运行验证五条状态轨道。简单任务不强制创建额外文件，复杂任务写入 `analysis-state.md`。

- 同一命令、查询或失败方法最多重复两次。第三次必须引入新证据、改变方法或标记阻塞。
- 新发现只有在改变下一步决策、结论或验证范围时才继续展开。
- 不因已经投入较多时间而继续错误分支。
- 恢复任务时先读取当前状态，不从头重复已通过关卡。

## 完成条件

| 模式 | 完成条件 |
|---|---|
| `analysis` | 回答目标问题；关键结论有证据；推断、待确认和局限已说明 |
| `runtime-validation` | 记录触发条件、运行样本、原始结果和主动干预结果；能回链静态或网络证据 |
| `patch-and-verify` | 修改范围可审计；构建、签名、安装、启动和目标行为分别有结果；未完成项如实报告 |

构建成功不能代替安装成功，安装成功不能代替启动成功，启动成功不能代替目标行为验证。
