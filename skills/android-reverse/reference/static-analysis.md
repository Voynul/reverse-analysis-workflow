# 静态分析规范

## 工具选择

Java/Kotlin 静态分析优先使用 MCP 服务 `jadx-headless`。不可用时可以使用经过验证的等价无头静态分析工具，并说明索引、搜索、交叉引用和源码质量能力差异。工具命名空间由当前 Agent 宿主决定，不探测、调用或回退到 JADX GUI MCP。

### 加载与目标确认

1. 用户明确给出的 APK、DEX、AAB、XAPK、APKM 或 JAR 绝对路径构成目标选择，可以调用 `load_apk`。
2. 加载后用 `current_apk`、`index_status` 和 Manifest 核对路径、包名、`versionName` 与 `versionCode`；发现不符时暂停。
3. 用户只给包名、功能描述或模糊目录时，不得自行挑选目标文件。
4. 服务中残留的目标只有在路径和身份信息与当前任务一致时才能沿用；状态文件存在时可作为辅助记录，但不能代替当前身份核对。
5. 不调用 GUI 专用接口，例如 `fetch_current_class`、`get_selected_text`、`debug_*` 和 `rename_variable`。

### 索引、源码质量与分页

1. 依赖完整索引的查询需检查 `index_status` 的状态和 `coverage_complete`，不能只看 ready。
2. `coverage_complete` 只表示搜索文档覆盖完整，不保证 Java 反编译完整。结合 `smali_fallback_classes`、`java_decompilation_complete` 和失败统计判断质量。
3. `get_class_source` / `get_method_by_name` 可能降级到 smali。检查返回的 `kind`、`fell_back`、`markers`；引用结论时标明实际证据来源。
4. 搜索结果检查 `source_kind` 和可用的 `source_note`。`java+smali` 命中不能描述为完整 Java 源码证据。
5. 文本工具按 `offset` / `max_chars` 和返回的 `*_page.next_offset` 继续读取；列表分页按工具 schema 的 `offset` / `limit` 操作。不能把单页内容当作完整结果。
6. 结果超过大小限制时缩小查询范围或分页，不重复提交相同的大查询。

### 故障处理

1. 连接中断时只执行一次轻量只读重试，例如调用 `current_apk` 或 `index_status`。
2. 重试失败后说明失败位置和已完成内容；可以使用经过验证的等价无头静态分析工具或 smali 补证，不回退到 GUI JADX。
3. 工具失败、索引失败或覆盖不完整只能证明当前证据不足，不能证明目标逻辑不存在。
4. 反编译明确超时或要求重启时，停止重复反编译。记录目标和进度，提示用户通过 MCP 宿主重启服务；重启后重新加载目标并检查索引。
5. JADX 反编译不清晰、控制流异常、泛型或匿名类难读时，可用 smali 或当前环境中的其他无头静态分析能力对同一目标做只读交叉验证，并说明原因。
6. 不同静态结果与 smali 不一致时，结合调用关系和运行时 Hook 判断。

### 生命周期

1. 服务默认由 MCP 宿主管理；中间汇报、等待补充或继续同一目标时保持运行。
2. 用户顺序切换目标时可调用 `load_apk` 重新加载，无需重启服务。
3. `clear_cache` 只清理内存源码缓存，不卸载目标，也不删除磁盘索引或重命名记录。
4. 只有用户明确要求关闭服务或释放进程内存时才调用 `shutdown_jadx`，参数为 `{}`。接口返回表示已发起退出，不代表已确认退出。
5. stdio 输入关闭后服务执行清理并退出；客户端保持连接但闲置时可能继续保留目标和内存。HTTP 无客户端时继续常驻，当前没有闲置自动退出保证。

## 常见入口

- `AndroidManifest.xml` 中的 Application、Activity、Service、Receiver、Provider。
- 用户给出的包名、类名、方法名、日志关键词、URL、字段名。
- SDK 初始化入口、点击事件、生命周期方法、网络客户端、加解密工具类。
- JNI 方法声明，例如 `native` 方法、`System.loadLibrary`、`RegisterNatives` 相关调用。

## 分析步骤

1. 查看 Manifest，确认组件、权限、入口和声明的 SDK 信息。
2. 搜索关键词，定位候选类、字符串、URL 和配置项。
3. 获取类源码和方法源码，阅读真实控制流。
4. 获取调用者和被调用者，补齐上游触发和下游结果。
5. 识别配置读取、分支判断、缓存读写、网络请求和回调。
6. 按后续分析需要理解混淆符号，并自主决定是否执行功能命名。
7. 对关键结论保存来源位置和代码片段。

## 混淆理解与命名

先理解混淆符号的功能，再决定是否需要工具内重命名或落盘。命名是提高分析效率和复用价值的可选手段，不是每次分析的强制产物。具体证据状态、命名依据和可选记录格式见 `evidence-and-renaming.md`。

工具操作和字段以当前服务的工具列表及 schema 为准。无头模式不为界面便利切换到 GUI。

## 搜索技巧

- JADX 的类搜索通常不适合直接输入带点完整路径，优先用短关键词。
- 查广告或聚合相关逻辑时，可搜索 `adapter`、`mediation`、`network`、`bid`、`impression`、`preload` 等关键词。
- 第三方公开 SDK 只作为边界和调用方确认，优先深入自建 SDK、混淆包和用户指定目标。

## 静态证据要求

每个关键判断必须记录：

- 类和方法位置。
- 原始混淆名；已经创建语义名称时同时记录可读名称。
- 判断条件或关键代码片段。
- 该代码影响的行为。
- 是否需要 Frida Hook、抓包或 native 分析继续验证。
