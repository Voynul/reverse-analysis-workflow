# 写作风格

## 总体风格

- 中性、清楚、可验证。
- 先讲结论，再讲证据。
- 用短句说明复杂逻辑。
- 每个关键小节末尾写一句总结。

## 推荐段落结构

````md
### 小节标题

本节说明这个机制解决什么问题。

触发时机：

- 什么时候执行。

关键逻辑：

- 做了什么判断。
- 依赖什么配置或数据。
- 结果影响什么行为。

证据：

```java
// 来源：原名→新名.方法名()
// 关键逻辑：一句中文解释
```

总结：一句话说明本节最重要的结论。
````

## 已检查但未发现的机制

报告中应保留读者容易误以为遗漏、但已经检查过的内容。没有实际检查过时，不得为了凑结构写“未发现”。

正文只展开真实存在且有证据支撑的内容。计划或用户问题覆盖但正文未展开的检查点，应在对应章节末尾使用简表说明。

| 分析点 | 状态 | 已检查范围 | 当前依据 | 补证建议 |
|---|---|---|---|---|

状态优先使用：

- 未发现：已检查相关代码、配置、网络样本或运行证据，但未发现对应机制证据。
- 不适用：目标没有对应形态、场景或触发条件。
- 待确认：当前材料不足，需要补充样本、配置、运行日志、抓包或 Hook 证据。
- 确认不存在：仅在检查范围足够闭合且证据可以支持不存在结论时使用。

最终汇总报告或大型阶段版报告中，只保留与核心结论相关、或读者容易误以为遗漏的“已检查但未发现”内容。零散搜索记录可以放入附录、证据索引或待确认问题，不必全部展开。

## 待确认问题

只记录证据不足、样本不足、来源冲突或链路不完整的问题。

不得把开发建议写入待确认问题。
