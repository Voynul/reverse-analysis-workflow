# 证据与字段规范

## 证据优先

- 每个关键结论必须有证据。
- 不得使用猜测、占位符、示例数据或省略号冒充真实证据。
- 字段名、类名、接口字段、SDK 包名只能作为线索。没有调用链、使用链、真实样本或运行证据时，必须写成线索、代码推断或待确认，不能写成确定事实。
- 如果任务来自分阶段分析计划，必须按计划阶段逐项落地；不能跳过证据确认后直接写总结。

## 字段说明

配置、参数、服务端策略、Firebase Remote Config 等字段含义说明，优先保留真实片段，并用字段旁注释解释字段含义、使用位置、证据等级和待确认问题。

不要默认拆成脱离原始结构的字段表。字段较多时，可以按配置模块分段展示注释片段；表格只作为索引、对比或汇总辅助。

原始 JSON、接口响应、缓存内容等证据必须另行保留未注释版本；报告正文可以使用 `jsonc` 注释版。

```jsonc
{
  "ad_show_count": 30 // 广告展示次数；证据：用于广告展示频控判断；证据等级：S2
}
```

## 核心流程

涉及核心流程的结论，正文必须还原真实静态代码流程，并尽量与真实网络数据、远程配置或缓存样本配对说明。代码和真实数据互相印证时作为最高强度证据；缺少任一侧证据时必须标注结论边界。

核心流程优先用以下结构呈现：

```text
真实数据来源 -> 关键代码判断 -> 状态变化 -> 结果动作
```

可以配流程图、调用链或短代码片段，但不能用伪代码替代真实代码。

## 静态代码说明

报告中引用静态代码、反编译代码、smali、调用链、关键方法或关键判断条件时，必须说明：

- 代码位置。
- 所属类或方法。
- 代码功能。
- 输入数据。
- 输出结果或状态变化。
- 对结论或业务行为的影响。
- 证据等级。

静态代码片段可以加阅读注释，但必须保持真实逻辑；不得改写逻辑、补造分支或用伪代码冒充真实代码。

## 用户同意与审计边界

报告不写安全、隐私、风险、合规等审计式评价，也不提出隐私合规建议。

可以描述用户同意状态、UMP、地区协议与 SDK 初始化、请求、展示之间的技术先后关系，例如：

- 同意状态完成前是否初始化 SDK。
- 同意状态完成前是否请求广告。
- 同意状态完成前是否展示广告。

这里只描述可观察到的技术事实，不评价是否合规。
