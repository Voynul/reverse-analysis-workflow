# 报告级别选择

## 核心原则

普通分析报告按任务大小自适应，不用为小任务硬凑大报告，也不能因为任务小就省略证据。

## 级别选择

| 级别 | 适用场景 | 必须保留 | 可省略 |
|---|---|---|---|
| 精简版 | 单字段、单接口、单方法、单开关、单次 Hook 结果 | 分析目标、结论、关键证据、待确认、总结 | 流程图、字段大表、已检查但未发现机制 |
| 标准版 | 一个专题、一条链路、一组字段、一个配置机制 | 流程或关系图、详细分析、证据索引、待确认 | 与主题无关的背景 |
| 阶段版 | 大型逆向任务中的阶段产物 | 阶段范围、前后关系、可合并结论、后续补证 | 最终报告里的全局重组 |

## 使用规则

1. 用户只问一个小问题时，用精简版。
2. 用户要求“写报告”“分析报告”且主题有完整链路时，用标准版。
3. 用户明确说阶段、分阶段、后续要汇总时，用阶段版。
4. 同一份普通分析报告可以直接交付，也可以成为最终报告的输入。
5. 最终报告负责多份报告的重组、取舍和冲突处理，普通分析报告不做跨报告合并。

## 结构取舍

- 小型报告不强制写“已检查但未发现的机制”；只有实际检查过、用户问过或读者容易误解时才写。
- 证据索引默认保留；如项目规则要求主报告精简，可拆为独立 `证据索引.md`，主报告只保留短证据锚点。
- 计划或用户问题覆盖但正文未展开的检查点，应在对应章节末尾用“分析点 / 状态 / 已检查范围 / 当前依据 / 补证建议”简表说明；状态优先使用“未发现 / 不适用 / 待确认”。
- 结论摘要优先使用“读者关心的问题 / 当前结论 / 可信度 / 依据”结构；不要用术语堆叠替代结论。
- 普通分析报告不负责合并多份报告；多报告汇总交给 `final-report`。

## 自检问题

输出前问自己：

1. 这个报告是否只回答一个点？如果是，用精简版。
2. 是否存在流程、关系、状态、时序或分支？如果是，需要配图。
3. 是否真的检查过某个机制不存在？如果没有，不写“已确认不存在”。
4. 是否后续要进入最终报告？如果是，保留证据索引和待确认问题。
